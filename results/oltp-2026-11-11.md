# 50,000건 주문 처리에서의 동시 조인과 다중 테이블 트랜잭션

**실험일** 2026년 11월 11일 · **시드** `20261111`

[GitHub Actions 실행](https://github.com/CheonYohan/db-type-benchmark/actions/runs/42969847891) · [측정 JSON](oltp-2026-11-11.json) · [실험 코드 커밋](https://github.com/CheonYohan/db-type-benchmark/tree/022ef46f752430a22f1e7f224a8917ee51951434)

## 초록

동일한 50,000건 주문 데이터에서 PostgreSQL, MySQL, MongoDB의 조회·주문 확정·혼합 부하를 동시 접속 1·4·16개에서 비교했다. 성공 커밋 처리량과 요청 지연을 측정하고, 커밋 직전 롤백을 포함해 재고·주문 상태·영수증이 예상값과 일치하는지 검증했다. 81회와 48,600개 논리 요청이 완료됐다.

## 1. 실험 방법

- **데이터** 고객 5,000명, 상품 256개, 주문 50,000건, 주문 항목 100,000건을 생성했다. 영수증은 빈 상태에서 시작했다. 주문마다 다른 상품 2개가 들어가며 주문의 80%는 동일한 8개 상품 집합에 재고 쓰기가 집중되도록 생성했다. 나머지 20%는 전체 상품에서 추출했다. 금액은 센트 단위 정수로 계산했다.
- **스키마** SQL은 고객·상품·주문·주문 항목·영수증 테이블과 외래 키를 사용했다. MongoDB는 같은 논리 모델을 컬렉션 5개와 `$lookup`으로 구현했다. 주문 고객 ID와 주문 상태, 주문 항목의 주문 ID에는 인덱스가 있다.
- **조인 조회** 한 주문의 고객·상품·항목을 결합해 두 행을 반환하는 4개 테이블 조인과, 한 고객의 주문 항목 수 및 총액을 계산하는 집계를 75:25로 섞었다.
- **주문 확정** 하나의 트랜잭션에서 주문과 두 항목을 읽고, 상품 ID 순서로 재고 두 건을 차감한 뒤 주문 상태를 변경하고 영수증을 삽입했다. 주문 확정 요청의 5%는 모든 쓰기 이후 커밋 직전에 실패시켰다. SQL은 `READ COMMITTED`와 `SELECT FOR UPDATE`, MongoDB는 단일 멤버 레플리카 세트에서 `snapshot` 읽기 및 `majority`·저널 쓰기 승인을 사용했다.
- **혼합** 조인 조회 70%와 주문 확정 요청 30%를 한 실행에서 섞었다. 엔진과 접속 수가 달라도 같은 회차에서는 같은 시드와 요청 목록을 사용했다. 회차마다 주문 상태, 재고, 영수증을 초기화했다.
- **측정** 엔진별·부하별로 동시 접속 1·4·16개를 각각 3회 측정했다. 회차당 600개의 고정 요청을 보내며, 접속마다 앞 요청이 끝나면 다음 요청을 시작했다. 연결 생성과 워밍업, 상태 초기화와 사후 검증은 측정 구간 밖에서 수행했다. 처리량은 3회 중앙값이며 p50·p95는 3회 표본을 합쳐 계산했다. 지연에는 SQL·드라이버·루프백 전송과 트랜잭션 재시도가 포함된다.
- **환경** 한 GitHub Actions Ubuntu 22.04 러너에서 세 엔진을 순차 실행했다. CPU는 AMD EPYC 7763 64-Core Processor, 노출된 논리 CPU는 4개, Python은 3.12.16이다. PostgreSQL 17.11, MySQL 8.4.13, MongoDB 8.0.34를 사용했다.

[PostgreSQL 행 잠금](https://www.postgresql.org/docs/17/explicit-locking.html) · [InnoDB 잠금 읽기](https://dev.mysql.com/doc/refman/8.4/en/innodb-locking-reads.html) · [PyMongo 트랜잭션](https://www.mongodb.com/docs/languages/python/pymongo-driver/current/crud/transactions/)

## 4. PostgreSQL 선택에 대한 해석

- **조회 중심 서비스** 동시 접속 1개에서 조인 조회는 MySQL이 초당 **2,661건**, PostgreSQL이 **1,814건**이었다. 동시 접속 4개에서는 PostgreSQL이 **4,282건/초**로 앞섰다. 이 결과에서 조회 부하의 순위는 동시 접속 수에 따라 달랐다.
- **조회와 주문 확정이 섞인 서비스** 동시 접속 16개에서 PostgreSQL은 **1,710요청/초**, 전체 p95 **35.39ms**였다. MySQL보다 처리량이 **49.9%** 높았다. 성공 커밋만 보면 같은 혼합 부하의 p95는 PostgreSQL **62.22ms**, MySQL **55.54ms**였다. 전체 API 처리량과 주문 확정의 지연 목표는 구분해서 판단할 필요가 있다.
- **주문 확정 전용 부하** 동시 접속 16개에서 PostgreSQL은 **743커밋/초**, MySQL은 **588커밋/초**였다. 성공 커밋 p95는 MySQL **55.03ms**, PostgreSQL **74.47ms**였다. 처리량을 우선하면 PostgreSQL이, 이 조건에서 주문 지연의 꼬리를 우선하면 MySQL이 앞섰다.
- **경합이 큰 다중 문서 쓰기** MongoDB는 동시 접속 16개의 주문 확정 전용 부하에서 세 회차 합계 **4,751회** 재시도했다. 전체 요청 p95는 **494.65ms**였다. 이 관측은 정규화 컬렉션 모델과 공유 재고를 갱신하는 트랜잭션에 해당한다.
- **동시성의 비용** PostgreSQL 혼합 부하에서 동시 접속을 4개에서 16개로 올렸을 때 처리량은 **1,993 → 1,710요청/초**, 전체 p95는 **5.68 → 35.39ms**였다. 접속 수는 데이터베이스 용량과 지연 목표를 기준으로 선택해야 한다.

## 5. 적용 범위

같은 정규화 모델과 8개 상품에 재고 경합이 집중되는 짧은 요청 부하를 비교했다. MongoDB의 문서 임베딩 모델, 다중 멤버 복제, 네트워크 왕복 지연, 커넥션 풀 대기와 장시간 부하는 별도 실험 조건이다. 부하별 순위는 엔진의 기본 성능뿐 아니라 SQL과 드라이버의 호출 경로, 잠금과 재시도 방식의 영향을 받는다. 회차당 600개 요청에서 얻은 수치이므로, 차이가 작은 경우에는 측정 JSON의 회차별 처리량을 함께 봐야 한다.

## 6. 재현

```bash
python3 -m venv .venv
. .venv/bin/activate
python -m pip install -r requirements.txt
export COMPOSE_FILE=compose.yaml:compose.oltp.yaml
export COMPOSE_PROJECT_NAME=db-type-oltp
docker compose up -d --wait
docker compose exec -T mongo mongosh --quiet --eval 'rs.initiate({_id:"rs0",members:[{_id:0,host:"localhost:27017"}]})'
for attempt in {1..30}; do
  docker compose exec -T mongo mongosh --quiet --eval 'quit(db.hello().isWritablePrimary ? 0 : 1)' && break
  sleep 2
done
docker compose exec -T mongo mongosh --quiet --eval 'quit(db.hello().isWritablePrimary ? 0 : 1)' &&
  python oltp_bench.py --orders 50000 --requests 600 --clients 1 4 16 --trials 3 --seed 20261111
docker compose down --volumes
```
