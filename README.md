# 50,000행 데이터베이스 CRUD와 보조 인덱스 실험

**실험일** 2026년 11월 11일 · **엔진** SQLite, DuckDB, PostgreSQL, MySQL, MongoDB

[성공한 GitHub Actions 실행](https://github.com/CheonYohan/db-type-benchmark/actions/runs/42964370408) · [측정 JSON과 실행 계획](results/crud-2026-11-11.json)

## 초록

같은 합성 데이터 50,000행의 삽입·읽기·수정·삭제를 기본키만 둔 조건과 보조 인덱스 세 개를 둔 조건에서 비교했다. 엔진당 각 조건을 세 번씩 실행하고, 초기 데이터와 수정된 데이터의 SHA-256 및 삭제 후 잔여 행 수를 확인했다. 보조 인덱스 조건에서 배치 삽입은 SQLite, 정렬 전체 읽기는 DuckDB가 가장 짧았다. 서버형 엔진 중 배치 삽입은 MongoDB가 가장 짧았다. 인덱스에 의한 조회 개선 폭과 쓰기 시간 변화는 엔진과 작업에 따라 달랐다.

## 1. 서론

같은 50,000행에 대해 삽입, 전체 읽기, 수정, 삭제의 처리 시간을 비교했다. 기본키만 둔 경우와 날짜·금액·UUID 보조 인덱스를 추가한 경우를 별도 테이블에서 실행했다. 이 설계로 인덱스가 조회 지연에 주는 효과와 전체 쓰기 과정에서 발생하는 유지 비용을 함께 관찰했다.

## 2. 자료 및 방법

### 2.1 데이터셋과 검증

### 2.3 CRUD 작업과 측정 방법

| 작업 | 측정 내용 | 결과 검증 |
|---|---|---|
| 삽입 | ID 순서로 50,000행 삽입. 보조 인덱스 조건에서는 적재 전에 빈 테이블에 인덱스 3개를 생성 | 전체 읽기에서 원본 SHA-256과 일치 |
| 전체 읽기 | ID 순서로 50,000행의 13개 필드를 조회해 Python 객체로 변환. 적재와 통계 갱신 직후, 선택 조회 워밍업 전에 실행 | 행 수와 SHA-256 비교. 해시 계산은 측정 구간 이후 수행 |
| 메모 수정 | 섞은 ID를 배치별로 지정해 비인덱스 필드 `note`를 `수정 완료`로 변경 | 두 수정 완료 후 전체 행의 SHA-256을 기준값과 비교 |
| 금액 수정 | 같은 ID 순서로 모든 행의 `amount`에 정확히 `0.2500`을 더함. 보조 인덱스 조건에서는 금액 인덱스도 갱신됨 | 수정된 모든 필드와 유지된 필드의 SHA-256 확인 |
| 삭제 | 같은 ID 순서로 모든 행을 삭제 | 남은 행 0개 확인 |

SQL은 배치별 트랜잭션을 사용했다. SQLite·PostgreSQL·MySQL은 다중 행 `INSERT`와 기본키 `IN` 조건을 사용했고, DuckDB는 컬럼과 ID 목록을 바인딩해 `UNNEST`로 펼쳤다. MongoDB는 독립 실행형 서버에서 `insert_many`, `update_many`, `delete_many`를 사용했다. MongoDB 쓰기의 원자성 단위는 개별 문서다. 쓰기 측정에는 값 변환, 드라이버 호출, 결과 전송과 커밋 또는 쓰기 승인 대기가 포함된다. 인덱스 구축 시간은 별도의 새 테이블에 50,000행을 채운 뒤 한 번 측정했다. SQL 엔진에서는 통계 갱신 시간도 포함했다.

### 2.4 선택 조회와 실행 계획

각 회차에서 조회 조건별 워밍업 3회와 측정 15회를 수행했다. 따라서 엔진과 인덱스 조건별로 필터 하나당 표본은 45개다. 기본키 조회는 회차당 시드로 뽑은 ID 40개를 15번씩 조회해 조건별로 1,800건을 측정했다. p50은 중앙값이며 p95는 오름차순 표본의 `ceil(0.95 × n)`번째 값이다.

**표 2. 읽기 작업의 조건과 검증 기준값**

| 작업 | 조건 | 기대 결과 |
|---|---|---:|
| 기본키 전체 행 조회 | 시드로 뽑은 ID 60개를 각 회차에 개별 조회 | 조회당 1행 |
| DATE 범위 건수 및 DECIMAL 합계 | `2023-06-30 ≤ day < 2023-07-30`에서 `COUNT` 및 `SUM(amount)` | 2,060행, 합계 `-64263.5210` |
| DECIMAL 범위 | `−125.4321 ≤ amount < 125.4321` | 1,238행 |
| TEXT 접두사 | `label`이 `sku-03`으로 시작 | 1,550행 |
| JSON 중첩 속성 | `payload.attributes.segment = "s03"` | 3,163행 |
| TIMESTAMP 범위 | `2023-06-30 12:00 ≤ event_ts < 2023-07-03 12:00` (UTC 기준) | 195행 |
| TIME 범위 | `08:30 ≤ clock < 09:00` | 1,067행 |
| BOOLEAN 및 INTEGER 조건 | `enabled = true` 및 `units ≥ 8000` | 2,566행 |
| DOUBLE 범위 | `−1.25 ≤ ratio < 1.25` | 104행 |
| UUID 일치 | `uid`가 표본 행의 UUID와 일치 | 1행 |
| BLOB 일치 | `raw`가 표본 행의 24바이트 값과 일치 | 1행 |
| NULL 필터 | `note`의 값이 `NULL` | 7,142행 |

범위 조건은 시작값을 포함하고 종료값은 제외한다. 날짜 범위는 건수와 합계를, 기본키 조회는 전체 레코드를 반환한다. 나머지 필터는 일치하는 행 수를 반환한다. TEXT는 SQL의 접두사 `LIKE`와 MongoDB의 접두사 정규식으로 구현했다. TEXT와 JSON 필터에는 보조 인덱스를 만들지 않았다.

날짜·금액·UUID 조건은 첫 회차에서 실행 계획을 별도로 수집했다. SQLite는 `EXPLAIN QUERY PLAN`, MySQL은 `EXPLAIN FORMAT=JSON`, PostgreSQL과 DuckDB는 `EXPLAIN ANALYZE`, MongoDB는 `explain`의 `executionStats`를 사용했다. 실행 계획 수집은 조회 지연 측정이 끝난 뒤 진행했다.

## 4. 보조 인덱스의 조회 효과

**표 4. 50,000행에서의 인덱스 구축 시간과 선택 조회 p50**

각 조회 셀은 기본키만 → 보조 3개 상태의 p50(ms)이다. 괄호의 배수는 기본키만의 p50을 보조 인덱스 조건의 p50으로 나눈 값이다. 날짜 범위는 2,060행(4.12%), 금액 범위는 1,238행(2.48%), UUID 조회는 1행(0.002%)과 일치했다.

| 엔진 | 보조 인덱스 3개 구축(초) | DATE 범위 집계 | DECIMAL 범위 | UUID 일치 |
|---|---:|---:|---:|---:|
| SQLite | 0.113 | 10.6175 → 3.9879 (2.66×) | 9.0328 → 0.0924 (97.74×) | 10.2088 → 0.0473 (215.84×) |
| DuckDB | 0.183 | 0.9607 → 0.9407 (1.02×) | 0.8176 → 0.8192 (1.00×) | 0.7247 → 0.5291 (1.37×) |
| PostgreSQL | 0.793 | 7.9988 → 1.5915 (5.03×) | 8.5300 → 1.1920 (7.16×) | 8.1721 → 0.3384 (24.15×) |
| MySQL | 0.288 | 9.9844 → 5.0966 (1.96×) | 10.5385 → 0.7719 (13.65×) | 9.0440 → 0.4678 (19.33×) |
| MongoDB | 0.278 | 17.8472 → 5.8310 (3.06×) | 22.9071 → 1.6851 (13.59×) | 17.7725 → 1.1670 (15.23×) |

**표 5. 첫 회차에서 관찰한 접근 방식**

| 엔진 | DATE 범위 집계 | DECIMAL 범위 | UUID 일치 |
|---|---|---|---|
| SQLite | `SCAN` → `SEARCH INDEX` | `SCAN` → `SEARCH COVERING INDEX` | `SCAN` → `SEARCH COVERING INDEX` |
| DuckDB | `Sequential Scan` → `Sequential Scan` | `Sequential Scan` → `Sequential Scan` | `Sequential Scan` → `Index Scan` |
| PostgreSQL | `Seq Scan` → `Bitmap Heap Scan + Bitmap Index Scan` | `Seq Scan` → `Bitmap Heap Scan + Bitmap Index Scan` | `Seq Scan` → `Index Only Scan` |
| MySQL | `ALL` → `range` | `ALL` → `range` | `ALL` → `ref` |
| MongoDB | `COLLSCAN` → `IXSCAN` | `COLLSCAN` → `COUNT_SCAN` | `COLLSCAN` → `COUNT_SCAN` |

DuckDB는 UUID 동등 조회에 인덱스를 선택했고, 날짜와 금액 범위에는 순차 스캔을 선택했다. 인덱스가 있을 때의 지연 차이는 실제 접근 방식과 함께 읽어야 한다. PostgreSQL에서 날짜 집계 p50은 **7.9988 → 1.5915 ms**로 줄었고, 50,000행의 금액 수정 시간은 **0.635 → 1.430초**로 늘었다. 자주 조회하면서 값도 자주 변경되는 필드에는 이 두 비용이 함께 적용된다. 기본키는 두 조건에 모두 정의했고, TEXT·JSON과 나머지 조회 작업에는 이번에 추가한 인덱스가 직접 적용되지 않는다.

## 5. 논의 및 DB별 추천

| DB | 추천 상황 | 이 실험에서 확인한 근거와 판단 조건 |
|---|---|---|
| **SQLite** | 오프라인 앱, 모바일·데스크톱 로컬 저장소, 단일 서비스 프로세스의 작은 데이터 저장 | 보조 인덱스 조건의 기본키 p50은 **0.0128 ms**, 50,000행 삽입은 **1.782초**였다. 파일에 직접 접근하는 구조가 적합하며 여러 작성자가 동시에 쓸 때는 대기와 잠금 시간을 측정해야 한다. [SQLite 사용 사례](https://sqlite.org/whentouse.html) |
| **DuckDB** | 로컬 SQL 분석, Parquet·CSV 탐색, 주기적 집계와 배치 데이터 처리 | 보조 인덱스 조건의 날짜 집계는 **0.9407 ms**, JSON 조건은 **9.2739 ms**였다. 인덱스 추가 후 금액 수정 시간 변화는 **+33.2%**였다. 이 드라이버 경로에서 정렬 전체 읽기는 **0.889초**, 배치 삽입은 **69.976초**였다. Parquet나 Arrow 기반 적재는 별도의 실험 조건이다. [DuckDB 분석 작업](https://duckdb.org/why_duckdb) |
| **PostgreSQL** | 주문·재고처럼 제약조건과 트랜잭션이 필요한 서버형 서비스, 관계형 데이터와 JSONB가 섞인 API | 보조 인덱스 조건의 기본키 p50은 **0.3272 ms**, 날짜 집계는 **1.5915 ms**였다. 조인과 여러 테이블에 걸친 트랜잭션이 필요한 경우에는 해당 쿼리와 동시 접속 조건으로 검증해야 한다. [PostgreSQL 기능](https://www.postgresql.org/about/) |
| **MySQL** | InnoDB 기반 웹 서비스, 기본키 조회와 인덱스 범위 검색이 중심인 기존 시스템 | DECIMAL 범위 조회 p50이 **10.5385 → 0.7719 ms**로 달라졌다. 금액처럼 범위를 자주 조회하면서 값도 자주 바꾸는 필드는 조회 개선과 갱신 비용을 함께 비교하는 것이 중요하다. [InnoDB 문서](https://dev.mysql.com/doc/refman/8.4/en/innodb-introduction.html) |
| **MongoDB** | 속성 구조가 다양하고 관련 데이터를 문서 단위로 함께 읽는 상품 카탈로그나 이벤트 수집 | 보조 인덱스 조건에서 배치 삽입은 **24,812행/초**, UUID 조회 p50은 **1.1670 ms**였다. 이 수치는 독립 실행 서버의 저널 승인 조건에서 얻었다. 복제 쓰기 승인과 여러 문서에 걸친 작업은 실제 구성에 맞춰 측정해야 한다. [MongoDB 문서 모델링](https://www.mongodb.com/docs/v8.0/data-modeling/embedding/) |

**실무에서 먼저 볼 지표**는 해당 서비스의 병목과 직접 대응하는 열이다. 적재가 병목이면 삽입 처리량과 배치 p95, API 조회가 병목이면 해당 조건의 p95와 실행 계획, 금액처럼 인덱스된 값이 자주 바뀌면 수정 처리량과 조회 개선 폭을 함께 비교할 수 있다.

## 6. 한계

- 이 결과는 50,000행과 단일 클라이언트에서 측정한 값이다. 서로 다른 배치 크기, 동시 접속, 조인, 분산 환경, 장기간의 쓰기 부하는 별도 실험 조건이다.
- 엔진별 전체 작업의 표본은 각 인덱스 조건에서 3회이며, 쓰기 배치 p95는 같은 실행 안의 150개 배치를 합친 값이다. 인덱스 구축은 별도 테이블에서 한 번 측정했다.
- 임베디드 호출과 루프백 통신, 드라이버의 인코딩, 정수·DECIMAL 표현, SQL 배치 트랜잭션과 MongoDB 쓰기 승인 방식의 차이가 포함된다. 수정·삭제는 해당 작업의 커밋 또는 승인 시점까지 측정했다. 이후 VACUUM과 저장 공간 회수는 별도 작업이다.
- TEXT와 JSON에는 전용 인덱스를 설정하지 않았다. 해당 검색이 주요 부하라면 별도 인덱스 설계와 선택도를 반영해 평가해야 한다.

## 7. 결론

보조 인덱스 채택 여부는 해당 조건이 실제로 인덱스를 선택하는지, 그리고 조회 지연 절감이 인덱스 구축과 갱신에 드는 시간을 감당할 만큼 큰지로 판단할 수 있다. 표 3~5는 이 판단에 필요한 쓰기 시간, 읽기 지연, 실행 계획을 같은 데이터로 비교한 결과다.

## 8. 재현 방법과 자료

Python 3.12와 Docker Compose가 필요하다. 서버 컨테이너의 포트는 로컬 루프백에 바인딩된다.

```sh
python3 -m venv .venv
. .venv/bin/activate
python -m pip install -r requirements.txt
docker compose up -d --wait
python crud_bench.py --rows 50000 --batch 1000 --seed 20261111 \
  --trials 3 --query-rounds 15 --points 40 --warmups 3 \
  --output results/latest-crud.json
docker compose down --volumes
```

표 3에 실제 DB 버전을 기록했다. 같은 패치 버전으로 재현하려면 Compose의 이미지 태그를 그 버전으로 지정한다.

SQLite 단독 실행은 Python 표준 라이브러리로 가능하다. 엔진을 지정할 때 `--engines`에 이름을 공백으로 나열한다.

```sh
python3 crud_bench.py --engines sqlite --output results/latest-crud.json
```
